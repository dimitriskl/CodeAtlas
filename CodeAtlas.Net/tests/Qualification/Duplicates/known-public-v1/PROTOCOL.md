# Frozen public fixture protocol v1

Prepared 20 October 2026 before detector draft creation. This small synthetic corpus is a development sanity check, not held-out evidence, representative business-code evaluation, or independent review. It contains 12 public methods and exactly 66 unordered pairs. No M7 held-out data or private application source was read. Labels were assigned by the same author who wrote the fixture; obtain fresh independent review before claiming qualification.

`labels.json` enumerates every pair, including unrelated pairs. Structural labels are `exact`, `renamed-near`, `near-with-rule-differences`, `different`, and `boilerplate`. Usefulness is independently labeled `review`, `domain-review`, or `no`; the `domain-review` class must never be silently counted as a useful duplicate. Identical trivial forwarders are structurally boilerplate and not useful review findings at default scope. The similar-documentation pair intentionally has different logic. Default-unrelated labels cover the remaining explicitly enumerated cross-family pairs, whose body operations and signatures were inspected during fixture authoring.

Freeze `Corpus.cs`, `labels.json`, and this protocol with SHA-256 in FREEZE.json before detector implementation/qualification. FREEZE.json is outside its own hash set. Record actual hashes/UTC timestamp, protocol version, detector revision, configuration, machine/toolchain and raw outputs for each later run. Never edit frozen inputs after seeing results: create a separately named v2 corpus and document why; retain v1 output. Hashing this fixture is preparation, not a detector execution or performance measurement.

Before any qualification run root/user accepts the proposed thresholds, work/result caps and performance budgets in ../PLAN.md; record that acceptance verbatim in the run report. Freeze detector/config before running. Report all 66 pairs with labels, eligibility/filter/unsupported status, candidate-generation considered or skipped status, emitted candidate status, scores and reasons/differences. Report true/false positives and false negatives against both (a) structural exact/renamed and (b) useful `review` pairs; report `domain-review` separately. Enumerate every false positive and false negative; do not select only attractive findings or imply perfect general accuracy from this tiny known corpus. Boilerplate filtering is an intended exclusion, not proof the methods differ.

The near-with-rule-differences pair has structural similarity with meaningful thresholds/discount changes. Returning it is acceptable only if changed constants remain in comparison evidence and the result says manual rule review is required. It is neither an exact nor a renamed-exact positive. A missed pair due to budget/seed restrictions remains an unexamined/recall limitation, never a negative behavioral result. Similar-purpose retrieval (documentation/facts, optional accepted local AI text) requires a separate frozen run and purpose labels; no provider is called by this detector.

Qualification must add fresh unseen public cases and independently reviewed private ignored application candidates later. They cannot replace this complete public report or borrow M7 sealed questions. Retain measured failures and caps.
